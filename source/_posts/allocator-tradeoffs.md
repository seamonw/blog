三种分配器都提供 `malloc` / `free`。调用方是 C、C++、Rust 还是别的语言，不改变下面的账单。账单只有三笔：锁等待、空闲内存占着的 RSS、对不齐的碎片。结构本身（tcache、arena、还页）见 [三种用户态分配器：ptmalloc、tcmalloc 与 jemalloc 的缓存和还页](/blog/2026/10/30/three-allocators/)。这里只写什么负载让某一笔变大。

数字来自 glibc 2.40 和 jemalloc 的默认值。没有「整体更快」这种结论：分配和释放在同一条线程上、且请求能命中本地缓存时，三者的热路径都是一次链表弹出。

## 同线程复用，差别在未命中

本地缓存命中时没有锁。优劣出现在缓存装不下、或者线程数把共享层挤满的时候。

```text
分配和释放在同一条线程
  命中本地缓存     三者都是无锁弹出，差距很小
  未命中
    ptmalloc      去抢某一把 arena 锁。64 位上，arena 超过 8 个之后上限是 8 * 核数
    tcmalloc      有 rseq 时按 CPU 取缓存，未命中再进 central free list
    jemalloc      进该线程绑定的 arena。arena 默认最多 4 * 核数
```

线程数接近核数、对象又小，ptmalloc 的 tcache 够用，不值得为了分配器再链一个库。线程数远大于 `8 * 核数`，而且小对象经常打不进 tcache（尺寸超过 1032 字节的 chunk，或 bin 里 7 个位置已满），多出来的线程会在少数几把 arena 锁上排队。这是 ptmalloc 的短板，不是「它有全局锁」。

tcmalloc 在支持 rseq 的 Linux 上把热缓存按 CPU 放。200 个线程、8 个 CPU，缓存份数是 8，不是 200。线程在 CPU 之间迁移时，缓存还留在原来的 CPU 上，不会跟着线程把空闲块搬走。没有 rseq 时退回每线程一份缓存，这个优势消失，内存按线程数涨。

jemalloc 的线程缓存默认开到 32 KiB 这一档，共享层是 arena，默认 `4 * 核数`。它不靠 rseq。线程远多于核时，未命中仍可能在 arena 上排队，但锁的个数通常比 ptmalloc 少一倍量级（4 倍核数对 8 倍核数，ptmalloc 的锁更多、单把锁上的人更少）。不要把「锁更多」直接写成「更慢」：每把锁上的等待者人数才是延迟。

## 释放发生在另一条线程，本地缓存帮的是释放方

`free` 把块放进**当前线程**的缓存，不是放回当初 `malloc` 的那条线程。生产者分配、消费者释放时：

```text
线程 P                         线程 C
malloc --> 从 P 的缓存弹出
把指针交给 C
                               free --> 推进 C 的缓存
P 再 malloc
  P 的缓存是空的 --> 未命中，去抢共享层
  C 的缓存里堆着 P 不再用的块
```

ptmalloc 的 tcache 就是这样。交叉释放把空闲块堆到释放线程上，分配线程继续付锁。消费者自己不分配这些尺寸的话，这批块要等它的 bin 满了才退回 arena，或者等线程退出。tcmalloc 和 jemalloc 也有线程或 CPU 本地缓存，交叉释放同样进不了分配方的缓存。差别是未命中之后的共享层：tcmalloc 用 central free list 做批量交接，jemalloc 把块还回 arena，ptmalloc 在 tcache 满之前根本不到 arena。

所以「换 tcmalloc 延迟会降」有一个前提：热点是同线程的小对象，或者未命中多到共享层成为瓶颈。分配和释放本来就在同一条线程、而且 tcache 命中，换分配器看不到差别。

## 延迟省下来的，RSS 会记上

本地缓存越宽，未命中越少，进程里闲置的空闲块越多。`free` 返回不表示页已经还给内核。

| | 占优的负载 | 付出的代价 |
| --- | --- | --- |
| ptmalloc | 线程不多，小对象，分配和释放同线程。没有额外依赖 | 线程一多且经常未命中，arena 锁排队。fastbin 不合并相邻小块，长期混尺寸会碎。`mmap` 阈值从 128 KiB 往上调，64 位最高到 32 MiB，阈值以下的块 `free` 后留在堆里 |
| tcmalloc | 小对象多、线程远多于 CPU、机器有 rseq。缓存份数跟着 CPU，不跟着线程 | 要单独链接或注入。没有 rseq 就退回每线程缓存，内存按线程涨。大对象不走 CPU 缓存，换它不改善这条路径 |
| jemalloc | 进程活得久，尺寸混杂，希望大块和小块分开。衰减时间可以改 | 默认 dirty 页大约 10 秒才衰减，这段时间 RSS 不降。每线程 tcache 收到 32 KiB。线程多时，空闲对象按线程数留着 |

glibc tcache 的上限可以算死。64 个 bin、每 bin 7 个、最大 chunk 1032 字节：一条线程最多 `64 * 7 * 1032 = 462336` 字节。200 条线程如果每个槽都塞满最大块，是 92467200 字节，约 88 MiB。实际每个 bin 的块更小，到不了这个数。它说明乘数是线程数，不是核数。

```go
package main

import "fmt"

func main() {
	const bins, fill, maxChunk = 64, 7, 1032
	perThread := bins * fill * maxChunk
	threads := 200
	fmt.Println(perThread, perThread*threads)
}
```

jemalloc 没有这么一个「每槽都是最大块」的单数字。它的 tcache 收到 32 KiB 这一档，档位数多于 64，空闲量仍然按活着的线程乘。tcmalloc 在 rseq 路径上按 CPU 乘。同样 200 个线程、8 个 CPU，缓存份数是 8。这是它在「线程很多、核很少」时 RSS 比另外两者低的原因，也是它依赖 rseq 的原因。

## 避坑

- **用单线程循环选分配器。** 循环里分配和释放在同一条线程，测到的是缓存命中，三者会挤在一起。要复现锁，就让线程数超过 arena 上限，并且让尺寸超过 tcache，或者让释放发生在另一条线程。
- **`LD_PRELOAD` 之后延迟没变，就认为分配器没用。** 注入只替换进程里走 libc `malloc` 的调用。已经静态链进别的分配器、或者自己用 `mmap` 做的池，不会经过这次替换。先确认热点栈上的分配函数是哪一个。
- **把衰减改成 0 来压 RSS。** `dirty_decay_ms = 0` 会在页变空闲时立刻 purge，小对象的复用变成反复找内核要页。延迟回来了，RSS 图好看了。要保留复用，就让衰减留着，把「RSS 高」和「泄漏」分开看。

## 面试重点

| 追问 | 答到这里可以停 |
| --- | --- |
| 什么时候三者差不多 | 小对象，分配和释放同一条线程，本地缓存命中 |
| ptmalloc 差在哪 | 未命中并且线程多于 arena。不是「每次 malloc 都有全局锁」 |
| tcmalloc 的优势依赖什么 | rseq 把缓存按 CPU 放。没有 rseq，缓存按线程涨 |
| jemalloc 的 RSS 为什么慢半拍 | dirty 页默认大约 10 秒衰减。这是复用空闲页的代价 |
| 交叉释放 | 块进释放线程的缓存。分配线程的下一次调用仍可能未命中 |

### 交叉释放不会把块还回分配线程

判据：分配栈和释放栈不在同一条线程，就不要用「本地缓存命中率」解释延迟。ptmalloc 在 tcache 未满时，这块内存不会回到 arena，别的线程拿不到。消费者线程如果只释放、不分配同一尺寸，它的 tcache 是净流入，生产者每次都未命中。把释放改回分配线程，或者让对象池按线程划分，比更换分配器先起作用。

### 32 MiB 以下的 free 可以一直不归还

ptmalloc 的 `mmap` 阈值默认 128 KiB，但会按分配习惯上调，64 位上限 32 MiB。上调之后，几十 KB 到几 MB 的块 `free` 掉仍留在堆上。用「超过 128 KiB 就一定会 `munmap`」判断 RSS，会把正常的阈值上调看成泄漏。阈值被环境变量设死时，动态上调才会停。

## 总结

同线程、小对象、缓存命中，三种分配器没有稳定的高下。ptmalloc 输在未命中后的 arena 锁和会碎的小块；tcmalloc 赢在缓存按 CPU 而不是按线程，前提是 rseq；jemalloc 用可调的衰减和分开的大块 arena 换长期运行时的碎片，默认多占大约 10 秒的 dirty 页。先看分配和释放是不是同一条线程，再看线程数和核数，最后看 RSS 允许滞后多久。
