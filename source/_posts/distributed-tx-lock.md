两笔扣款只应该发生一笔。人会加一把 Redis 锁，或者上两阶段提交。锁到期之后进程还会写；协调者在发出提交之前崩溃，一个参与者已经提交，另一个会回滚。保护结束的时刻和写入结束的时刻不是同一个时刻。

事务是一组写要么都留下、要么都不留下。分布式锁是一份带过期时间的租约，用来让临界区在一段时间里只有一个持有者。租约不是回滚。一次远程调用返回成功，只说明响应到了，不说明两边都提交了，见 [RPC 原理、Go net/rpc 与一份极简实现](/blog/2026/09/04/rpc-from-scratch/)。

## 先把 COMMIT 写进稳定存储，再发给参与者

两阶段提交里，参与者对 PREPARE 投了 YES，就把本地行锁占住，等协调者的决定。此后它不能自己回滚：协调者可能已经让另一边提交了。协调者如果在写出决定之前崩溃，这些参与者一直占着锁。这是 2PC 的阻塞点。

决定本身只有一种安全顺序：协调者先把 COMMIT 记录 `fsync` 到稳定存储，然后才向任何一个参与者发送 COMMIT。写进 page cache 不算。崩溃恢复时，日志里有 COMMIT 就把剩下的参与者提交完；没有这条记录就全部中止（presumed abort）。ABORT 可以不先强制落盘，因为默认决定就是中止。COMMIT 和 ABORT 不对称。

```text
协调者日志                 P1                      P2
PREPARE ---------------> 投票 YES，占住行锁
PREPARE --------------------------------------> 投票 YES，占住行锁

错序：
  COMMIT 消息 ---------> P1 已提交
  崩溃，磁盘上没有 COMMIT 记录
  恢复后按「没有记录就是中止」告诉 P2 回滚
  结果：P1 提交，P2 回滚

正序：
  fsync(COMMIT 记录)
  COMMIT 消息 ---------> P1
  COMMIT 消息 -----------------------------> P2
  发完之前崩溃也没关系，新过程读到同一条记录，两边都提交
```

把这条记录放进 Raft 一类的多数派日志，协调者机器坏了，新 leader 还能把 COMMIT 发完。这去掉的是单份磁盘。准备阶段参与者占着的行锁还在，占用时间和协调者恢复时间一样长。

参与者投了 YES 之后自己超时回滚，就是上面的错序，只是不需要协调者崩溃来触发。它已经投过 YES，超时只说明决定还没送到，不说明决定是中止。

## 租约到期不等于临界区已经停手

锁服务把一把锁交给 A，并写上 TTL。A 被 GC 或页错误暂停，TTL 走完，锁服务把锁交给 B。A 醒来继续写。锁记录上此时只有 B，资源上 A 和 B 都在写。

多数派锁（例如向 5 个独立节点抢到 3 个）只让锁记录最终有一个持有者。它不证明上一个持有者的进程已经停住。锁记录若还能让两个人同时认为自己持有，连这一步都不成立，见 [线性一致性：多数派读写为什么还会出现新值变旧值](/blog/2026/10/28/linearizability-quorum/)。

能挡住暂停的是 fencing token：锁服务每次授锁发一个只增不减的序号。资源在同一次修改里拒绝更旧的序号。

```text
锁服务                 A（token=1）            资源                 B（token=2）
授锁 1  ------------>
        暂停，超过 TTL
授锁 2  -------------------------------------------------------->
                                            B 以 2 扣款，fence=2
        醒来，仍以 1 扣款
                                            1 < 2，拒绝
```

序号必须和业务写在同一次原子操作里比较。先问锁服务「我还持有吗」，得到是，再去写库：两次调用之间租约会过期，问到的答案已经作废。数据库用一行里的 `fence` 列，或者存储自己的单调修订号，和余额改动放在同一个本地事务里。

etcd 的锁把 key 的创建修订号交给持有者，租约到期 key 被删掉。修订号可以当 token。资源不比较这个号，锁白拿。

## 旧序号要在资源上失败

下面这段是资源侧的模型，没有网络和磁盘。B 先用 token 2 扣 40，A 再用 token 1 来扣。检查序号时 A 被拒绝，余额是 60。不检查时两笔都进去，余额是 20。

```go
package main

import "fmt"

type store struct {
	balance int
	fence   uint64
}

// 比较和改余额在同一次调用里。拆成两次 RPC，中间租约会过期。
func (s *store) apply(token uint64, delta int) error {
	if token < s.fence {
		return fmt.Errorf("reject token %d, store has %d", token, s.fence)
	}
	s.fence = token
	s.balance += delta
	return nil
}

func (s *store) applyUnchecked(delta int) {
	s.balance += delta
}

func main() {
	fenced := &store{balance: 100}
	if err := fenced.apply(2, -40); err != nil { // B 在 A 暂停期间拿到更新的 token
		panic(err)
	}
	err := fenced.apply(1, -40)
	fmt.Println(err)                      // reject token 1, store has 2
	fmt.Println("fenced", fenced.balance) // 60

	open := &store{balance: 100}
	open.applyUnchecked(-40)
	open.applyUnchecked(-40)
	fmt.Println("unchecked", open.balance) // 20
}
```

`token < fence` 才拒绝，相等的序号还能再执行 `delta`。那是同一次持锁里的第二笔扣款，也可能是第一笔成功之后的重放。fence 分不清这两件事。重放要另记请求编号，编号见过就返回上次的结果，不再改余额。

## 避坑

- **`SET key NX PX` 当成互斥。** 过期、主从切换、客户端暂停都会出现两个写者。改法：授锁时发只增序号，资源的同一条本地事务里比较序号；或者直接用资源自己的条件更新（`UPDATE ... WHERE fence < ?`），不另起一个锁服务。
- **两把本地事务外面套一把锁。** 锁还在，进程在第一把事务提交后、第二把开始前崩溃。第一边已经持久化，锁不会把它撤掉。要两边同时提交，得有协调者的 COMMIT 记录。只是不想并发执行，才用锁。
- **准备之后用本地超时中止。** 参与者投 YES 之后启动一个定时器，到点回滚并释放行锁。另一边可能已经收到 COMMIT。改法：定时器只负责告警和重问协调者；中止只接受协调者的决定，或者接受一份含有 COMMIT 记录的恢复结果。

## 面试重点

| 追问 | 答到这里可以停 |
| --- | --- |
| 2PC 哪一步会卡住 | 参与者投了 YES，协调者的决定还没到。这段时间不能自己回滚 |
| COMMIT 的顺序 | 先 `fsync` COMMIT 记录，再发 COMMIT。没有记录就中止 |
| 锁保证了什么 | 锁记录上的持有者。不保证持有者的进程还在跑，也不回滚已经提交的本地事务 |
| 暂停超过 TTL | 旧持有者还会写。资源用更大的 fencing token 拒绝它 |
| 锁和事务怎么选 | 要互斥用锁加 token，或用资源上的条件写。要多边原子提交，用带稳定决定记录的提交协议 |

### 3PC 过不了分区

3PC 在「进程崩溃即停止、消息延迟有上界」时，可以用超时把参与者从「等决定」里放出去。分区不满足这个假设。切开的两边各自凑超时，一边提交、一边中止，和错序的 2PC 是同一个结局。面试里说「3PC 解决了 2PC 的阻塞」，要把失败模型补上；补不上，这句话不成立。

### 补偿不是原子回滚

Saga 让每一步先在本地提交，失败再跑补偿动作。补偿是另一笔业务写，不是把上一笔从日志里抹掉。库存已经扣了、补偿请求又超时，系统里同时存在「扣过」和「不知道补没补上」。补偿动作本身要能安全重放。需要读到的中间状态对别人不可见时，Saga 的隔离不够，还是要回到会占住锁的提交协议。

## 总结

2PC 的正确性在 COMMIT 记录的落盘顺序：没有这条记录就不能发出提交，投了 YES 的参与者就不能自己中止。分布式锁的正确性在资源侧的序号：租约只负责把锁记录收回，不负责让上一个进程停手。锁外面套两段本地提交，既没有原子性，也没有暂停之后的互斥。
