「负载因子 6.5，一个桶 8 个 key，溢出桶挂链表。」这是 Go 1.23 及以前的 `hmap`。Go 1.24 换成 Swiss Table，Go 1.27 的 `internal/runtime/maps` 仍是这套。两套都要能说，但别把旧桶当成现在的内存布局。

## 一组 8 个槽，用一个控制字一起比

一个 group 有 8 个槽，外加 8 字节控制字，每槽 1 字节：

```text
ctrl:  empty | h2 | h2 | deleted | empty | h2 | h2 | h2
        10000000  0hhhhhhh        11111110

slots: k0 v0 | k1 v1 | ... | k7 v7
```

控制字节只有三种，高位决定状态：

| 状态 | 位型 | 含义 |
| --- | --- | --- |
| empty | `10000000` | 空。探测到含 empty 的 group 就可以停 |
| deleted | `11111110` | 墓碑。删过，探测不能在这里停 |
| full | `0hhhhhhh` | 占用。低 7 位是哈希的 H2 |

哈希拆成两段。低 7 位是 H2，塞进控制字节。高 57 位是 H1，用来选 group。查找时 8 个 H2 一起和目标比，命中的槽再做真正的 key 比较。H2 只有 7 位，大约 1/128 的概率碰对但 key 不同，所以控制字命中永远不算找到。

group 的数量是 2 的幂。探测序列是

```text
p(i) = H1 + (i² + i) / 2    （对 group 个数取模）
```

2 的幂个数下，这条序列会走过每个 group 恰好一次。表不能装满：探测靠 empty 收尾，没有 empty，查找停不下来。

key 或 value 超过 128 字节（`MapMaxKeyBytes` / `MapMaxElemBytes`）不放进槽里，槽里只留指针。

## 扩容是整张表重排，所以一张表不能太大

探测步长取决于 group 个数。group 一变，所有槽都得按新序列重摆，一张表只能整个长大，做不到旧实现那种「搬一个桶算一个桶」。

单表太大时，这次重排就会卡住。Go 1.27 把单表容量封在 `maxTableCapacity = 1024` 个槽。这个常数在源码注释里写明是待调的，不是协议。不到这个上限，增长就是换一张两倍大的表。到了上限，表拆成两张，每张仍是 1024 槽。

多张表用可扩展哈希选：哈希的高位做目录下标。一张表时目录长度 1，不用看哈希。拆成两张时用 1 位，四张时用 2 位。各表装得不一样满，目录里可以有两项指向同一张表：

```text
directory (globalDepth = 2)
  00 ──┐
  01 ──┴─► table A   localDepth = 1
  10 ────► table B   localDepth = 2
  11 ────► table C   localDepth = 2
```

每张表自己算负载。一组 8 槽，`maxAvgGroupLoad = 7`，平均超过 7/8 就长。这和旧实现的 6.5/8 是同一类阈值，数字不同，触发的动作也不同：旧的是搬进两倍桶并增量疏散，新的是整表重排，或在目录上拆表。

删除要保住「遇到 empty 才能停」。组里还有 empty 时，被删的槽直接标 empty。组已经满了，槽标成墓碑，否则后面的探测链会在这里被截断。墓碑留到下次增长才清掉。插入优先填墓碑，再占 empty。

## 和 Go 1.23 的桶对照

面试官若还按旧结构问，把两套分开说。

| | Go 1.23 及以前 | Go 1.24 起（含 1.27） |
| --- | --- | --- |
| 槽 | 每桶 8 个 key，桶外挂溢出链 | 每 group 8 个槽，开放寻址 |
| 快速比较 | `tophash` 一字节 | 控制字里的 H2，8 个一起比 |
| 冲突 | 溢出到下一个桶 | 二次探测下一个 group |
| 装载 | 平均 6.5 / 8 | 平均 7 / 8（`maxAvgGroupLoad = 7`） |
| 变大 | 桶数翻倍，写入时增量疏散 | 单表整表重排；超过 1024 槽则拆成两张表 |
| 删除 | 覆盖或清空 tophash | 有 empty 就标 empty，否则留墓碑 |

迭代的语义两套一样，来自律例，不来自某一种布局。Go 1.27 源码把这五条写在 map 的注释里：

- 迭代期间新增或删除，同一个元素不能返回两次
- 迭代期间新增的，可以出现，也可以不出现
- 改过的元素，必须看到新值
- 删掉的元素，不能再被返回
- 顺序不确定。实现里会故意随机起点

```go
package main

import "fmt"

func main() {
    m := map[int]int{1: 1, 2: 2, 3: 3, 4: 4}
    for k := range m {
        if k%2 == 0 {
            delete(m, k)
        }
    }
    fmt.Println(m) // 只剩奇数 key。删当前 key 是安全的
}
```

循环里 `m[k+10] = 1` 则没有这种保证，新 key 可能被走到，也可能不被走到。不要靠这个写逻辑。

## 避坑

- **并发读写不是 panic。** 同时读写会 `fatal error: concurrent map read and map write`（或 concurrent map writes），进程直接死，`recover` 接不住。要并发就换锁，或者换数据结构，不要包一层 `recover` 当防护。
- **`NaN` 当 key。** `math.NaN() != math.NaN()`，每次插入都是新槽，`m[math.NaN()]` 读不回来。Go 1.27 上连续插两次，`len` 是 2，读取得到零值。float64 当 key 时先处理 NaN。
- **key 必须可比较。** slice、map、函数不能当 key。结构体里嵌了这些也不行。接口当 key 时，比的是动态类型和动态值，类型不同就是不同的 key。

`sync.Map` 不是带锁的 map。它适合 key 稳定、读多写少的那一类，写多的时候常常比 `Mutex` + map 更差。面试里说「要并发就用 sync.Map」这句不够。

## 面试重点

| 追问 | 答到这里可以停 |
| --- | --- |
| 现在的结构 | Swiss Table。8 槽一组，控制字并行比 H2，二次探测。1.23 及以前才是桶加溢出链 |
| 为什么不能 100% 满 | 探测遇到 empty 才停。满表没有收尾 |
| 删除为什么有时留墓碑 | 组里没有 empty 时，标 empty 会把后面的槽从探测链上剪掉 |
| 怎么变大 | 平均超过 7/8 就长。单表整表重排；Go 1.27 单表超过 1024 槽则在目录上拆开 |
| 迭代能改吗 | 删当前 key 可以。插入不保证可见。顺序不能依赖 |
| 并发 | 运行时直接 fatal，不是可恢复的 panic |
| 为什么遍历顺序每次不同 | 规范规定无序。实现会随机起点，避免用户依赖顺序 |

## 总结

map 是哈希表这件事没变，变的是碰撞怎么放、变大时搬多少。Go 1.24 之后回答 group、控制字、整表重排和目录拆分。旧的 6.5 和溢出桶只用来回答「1.23 以前是什么样」。并发问题不在负载因子，在这张表根本没有锁。
