三个副本，写只落到一台。读若碰上这台，会把还没形成多数派的值返回给调用方。下一次读没碰上它，值又变回去。`R + W > N` 挡不住这个窗口。

副本是同一份数据的多份拷贝。法定人数是一次操作必须联系上的副本数。线性一致要求每个操作在「调用」和「返回」之间的某个时刻生效，并且真实时间上已经结束的操作，排在它后面的操作必须看得见它。

一次 RPC 返回成功，只说明响应到了客户端，不说明效果已经在多数派上。这个第三态见 [RPC 原理、Go net/rpc 与一份极简实现](/blog/2026/09/04/rpc-from-scratch/)。

## 读到未完成的写，下一次读可以把它丢掉

`N = 3`，写法定人数 `W = 2`，读法定人数 `R = 2`。`2 + 2 > 3`，任意一次读和任意一次已完成的写至少共用一台机器。条件是「写已经完成」，也就是值已经落在 `W` 台上。

写还停在 1 台上时，这个条件不成立。读却可能先看到它：

```text
节点     A          B          C
初值    v0         v0         v0

写 v1   已写入      没到        没到      写未完成（不到 W=2）

读 R1   读到 v1     —          读到 v0    取最大版本，返回 v1，R1 结束
读 R2    —         读到 v0     读到 v0    R1 已结束后才开始，返回 v0
```

R1 在 R2 之前结束，R1 看见 v1，R2 看见 v0。线性一致不允许已经读到的值再消失。交集保证的是「已完成的写不会被错过」，不是「未完成的写可以先被读走」。

修法是读在返回之前，把看到的最大版本写回自己的读法定人数（ABD 算法的 write-back）。R1 的读集合是 `{A, C}`，返回前 C 上也有了 v1。R2 读 `{B, C}`，在 C 上碰到 v1。写回没凑满法定人数，这次读不能返回成功，否则窗口还在。

## 旧 leader 上的读，和日志选主不是同一件事

Raft 把已提交日志交给新 leader：候选人的日志必须包含全部已提交条目，否则不能当选。这只保护「已经复制到多数派的写」。它不保护读。

旧 leader 在分区一侧仍以为自己是 leader，用本地已提交索引回答读。另一侧新 leader 已经提交了更新的条目。这次读错过的是一次已经完成的写。

```text
L1（旧 leader）          多数派              L2（新 leader）
本地已提交 index=5
        分区，L1 联系不上多数派
                                            当选，提交 index=6
客户端读 L1，得到 5
                                            客户端读 L2，得到 6
```

读 5 的请求若发生在 index=6 提交之后，真实时间上的后读看见了更旧的状态。Raft 论文第 8 节的处理是：应答只读请求之前，leader 先和多数派交换一次心跳，确认自己仍是 leader。用租约省掉这次往返时，租约长度必须盖过时钟误差；误差不知道上界，租约就不再安全。

跟随者直接读本地状态机，和旧 leader 是同一类错误。要线性读，读必须走仍握有领导权的那一台，或者走带写回的法定人数。

## 把窗口跑出来

下面这段只模拟三台机器上的版本号，不处理丢包和并发写。它把上一节的两次读跑出来：不写回时结果是 `1 0`，写回后是 `1 1`。

```go
package main

import "fmt"

type reg struct {
	val int
	ver int
}

// 读满整个法定人数再取最大版本。先到先回会把没收集齐的旧值当成结果。
func readMax(n []reg, q []int) (int, int) {
	bestVal, bestVer := 0, -1
	for _, i := range q {
		if n[i].ver > bestVer {
			bestVer = n[i].ver
			bestVal = n[i].val
		}
	}
	return bestVal, bestVer
}

func writeBack(n []reg, q []int, val, ver int) {
	for _, i := range q {
		if n[i].ver < ver {
			n[i].val = val
			n[i].ver = ver
		}
	}
}

func main() {
	// ver=1 只在节点 0，写法定人数 W=2 没达到。
	naive := []reg{{1, 1}, {0, 0}, {0, 0}}
	r1, _ := readMax(naive, []int{0, 2})
	r2, _ := readMax(naive, []int{1, 2})
	fmt.Println("naive", r1, r2) // 1 0

	fixed := []reg{{1, 1}, {0, 0}, {0, 0}}
	v, ver := readMax(fixed, []int{0, 2})
	writeBack(fixed, []int{0, 2}, v, ver) // 返回 v 之前必须写回成功
	r2b, _ := readMax(fixed, []int{1, 2})
	fmt.Println("writeback", v, r2b) // 1 1
}
```

并发的两个写需要全序的版本号，常用「逻辑时钟 + 写入者编号」打破平局。用墙上时钟，回拨的一方会把较新的值盖掉。这段代码把版本号当成已经比好的整数，没有覆盖这个失败。

## 避坑

- **先到先回。** 读请求把第一个响应交给调用方。那一台可能不在上一次写的法定人数里。改法：收满 `R` 个响应再取最大版本；超时没满就返回错误，不要返回半截结果。
- **版本用 `time.Now()`。** 两台机器时钟差几秒，旧写带着更大的时间戳落在法定人数上，新写被丢掉。改法：版本由副本上见过的最大版本加一，或由单一分配者发放。时钟只用来超时，不用来比谁更新。
- **重试一次非幂等写。** 第一次写已经进了多数派，响应丢了，客户端再写一遍，计数器加两次。寄存器覆盖写可以带同一个版本重试。递增、扣库存要有调用方生成的请求编号，副本认编号，不认「又来了一次」。

## 面试重点

| 追问 | 答到这里可以停 |
| --- | --- |
| 线性一致在约束什么 | 操作在调用和返回之间生效；真实时间上先结束的，后开始的必须看得见 |
| `R + W > N` 保证什么 | 已完成的写和之后的读有交集。未完成的写不在这个保证里 |
| 为什么还要写回 | 读若提前看见未完成的写，要把这个值推进到一个读法定人数，然后才能返回 |
| 旧 leader 为什么不能直接读 | 日志选主保住已提交的写。读还要确认这台现在仍是 leader |
| 跟随者读 | 本地状态机是过去的已提交前缀，不是线性读 |

### 不等式是严格大于

`R + W = N` 时交集可以为空。`N = 3`，`W = 2`，`R = 1`：写在 `{A, B}` 上完成，读打到 `C`，读不到。`N = 4` 时多数派是 3，不是 2；`2 + 2` 不大于 4，写 `{A, B}` 和读 `{C, D}` 没有公共副本。

### 线性一致不是可串行化

可串行化说的是多个对象上的事务，存在某种串行顺序，不要求这个顺序等于真实完成时间。事务 T1 真实时间上先提交，T2 后提交，串行顺序仍可以是 T2 然后 T1。线性一致不允许这件事。事务上的对应物是严格可串行化：可串行，再加上真实时间。把两个词换成同一个，读写协议和事务隔离会答到对方的题上。

## 总结

多数派相交只保证已完成的写能被后来的最大版本读看见。读可以先碰上未完成的写，写回之前就返回，这个值会在下一次读消失。Raft 里同一形状的错误是旧 leader 不确认领导权就应答读。
