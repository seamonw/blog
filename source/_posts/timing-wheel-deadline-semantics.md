时间轮最容易被误解的地方，不是环形数组，而是那句“插入和执行都是 O(1)”。

设想一个长连接网关：需要维护大量连接的空闲超时，连接活跃时不断重置 deadline，绝大多数定时器最终被取消，只有少数真正到期。这里是**假设场景，不是实测案例**。如果允许毫秒到几十毫秒级的量化误差，时间轮可能比维护所有 deadline 的精确顺序更合适；但同一时刻涌入大量到期任务，依然会制造长队列。

**时间轮优化的是时间索引的维护方式，不是把任务执行成本变没。**一套可用于生产的定时器，还必须回答：会不会提前触发？整圈边界怎么处理？取消成功究竟承诺什么？暂停之后如何追赶？

本文围绕五个问题展开，以 Go 给出可运行的单线程验证模型。代码不是生产定时器，也不是某个库的源码复刻。源码对照分别注明版本或资料范围，不把历史实现描述为最新版本。

## 一、先定义定时器语义，再比较数据结构

### 1.1 我们真正要维护的不是“睡眠”，而是截止时间

一个最小定时器接口有三类操作：

- `Schedule(deadline, callback)`：注册一个截止时间。
- `Cancel(handle)`：尝试阻止该次注册的回调开始执行。
- `Advance(now)`：识别已经到期的任务，使它们进入执行路径。

本文选择的语义是：**不早于 deadline；允许因量化、推进和执行排队而延后；单次注册最多获得一次执行权。**这里“最多一次”限定在进程内的一次注册，不等于业务副作用的分布式 exactly-once。

必须进一步区分三个时刻：

1. **截止时间到达**：时钟满足 `now >= deadline`。
2. **任务被发现并就绪**：定时器完成扫描，把任务交给执行路径。
3. **回调开始运行**：执行器真正获得 CPU，进入回调函数。

一个精确排序的堆，也只能帮助找到最早 deadline，不能让第三个时刻精确等于第一个。

### 1.2 合理基线是带索引的最小堆

不要用“每次扫描所有任务”的低效方案衬托时间轮。带节点索引的最小堆本来就是很好的基线：

| 结构 | 注册 | 已知任务的取消 | 发现到期任务 | 额外约束 |
|---|---|---|---|---|
| 带索引最小堆 | O(log n) | O(log n) | 看堆顶 O(1)，逐个弹出 O(log n) | 元素移动时维护索引；无时间分桶误差 |
| 单层时间轮＋圈数 | 定位、挂链 O(1) | 持有效双向链表节点时摘链 O(1) | 扫描当前桶 O(m)，包括未到期节点 | 精度离散化；长任务每圈被访问 |
| 经典层级时间轮 | 逐层定位 O(L)，挂链 O(1) | 同样可 O(1) 摘链 | 到期扫描＋级联搬迁 | 层级、范围、级联和唤醒索引都要管理 |

`n` 是任务数，`m` 是当前被处理桶的节点数，`L` 是层数。表中不包括锁等待、内存分配、消息排队、回调执行，以及额外唤醒索引的维护。

普通堆若只有任务 ID、没有位置索引，随机取消可能先花 O(n) 找元素；若用懒删除，则要把取消对象的留存和后续清理计入成本。比较必须统一取消语义和清理口径。

**什么时候先不做时间轮？**定时器规模和 churn（频繁注册、取消、重置）尚未形成热点、deadline 精度要求高、或者框架已经提供与事件循环集成良好的定时器时，保留堆通常更容易维护。先测量，不要把 O(1) 当作迁移理由。

## 二、单层时间轮：难点在绝对时间与整圈边界

### 2.1 先固定游标含义，公式才有意义

设：

- `u`：一个 tick 的时间长度。
- `N`：槽位数。
- `t0`：单调时钟的共同起点。
- `c`：**已经完整处理完毕**的逻辑 tick。
- `d`：某任务计划就绪的逻辑 tick。

推进时先令 `k = c + 1`，处理槽位 `k % N`，全部处理完后才提交 `c = k`。新注册命令在两个 tick 之间应用；级联中的内部搬迁稍后单独讨论。

环形数组只做一件事：把目标 tick 相同余数的任务放在同一个槽里。

```text
N = 8
槽位    0    1    2    3    4    5    6    7
目标    8    1    2    3    4    5    6    7
       16    9   10   11   12   13   14   15
       24   17   18   19   20   21   22   23
```

仅有槽位不能区分 `d=1`、`d=9`、`d=17`。单层 hashed wheel 为每个节点增加剩余圈数。

### 2.2 必须从绝对 deadline 向上取整

对于 owner 收到命令时仍未过期的任务，先计算：

```text
D = ceil((deadline - t0) / u)
d = max(c + 1, D)
slot = d % N
rounds = floor((d - c - 1) / N)
```

若 `deadline <= now`，直接走就绪路径，不要把它重新挂进已经扫描过的历史槽；就绪仍要经过取消状态检查。

为什么不能简单写成 `c + ceil(delay/u)`？因为 `c` 对应的是已处理刻度，而注册时刻可能处于一个 tick 中间。

**反例：**`u=10ms`、`t0=0`，当前实测时间为 `105ms`，已处理到 `c=10`。此时注册“10ms 后执行”：

- 真正 deadline 是 `115ms`。
- 正确目标是 `ceil(115/10)=12`，名义就绪刻度为 `120ms`。
- 错误捷径得到 `10 + ceil(10/10)=11`，在 `110ms` 扫描时会提前 `5ms`。

如果错误捷径再补一个 deadline 检查，提前执行虽然可能被拦住，但任务仍需被正确重定位；若只是留在原槽，可能又晚一整圈。

这里隐含三个不变量：`u>0`；时钟、deadline、t0 属于同一单调时钟域且运算不溢出；`c<=floor((now-t0)/u)`。对于未来 deadline，这使 `D>=c+1`，因此 d 就等于 D。

对于正常轮内路径，向上取整的**纯量化误差**满足：

```text
0 <= (t0 + d*u) - deadline < u
```

这个结论要求未来任务正常按绝对 deadline 定位、游标未错误超前。它不是实际回调延迟的上界。

工程实现还要检查 deadline 相加、时间差、跨度乘法和 tick 计数器溢出。正整数向上除法宜使用 `x/u + bool(x%u != 0)`，而不是可能溢出的 `(x+u-1)/u`；超出支持范围应明确拒绝或走溢出结构，不能悄悄截断。

### 2.3 `rounds` 中的减一，保护的是整圈边界

在前述“处理下一格”的约定下，访问一个节点时：

```text
rounds > 0：rounds--，留在桶中
rounds = 0：到期，摘下并进入就绪路径
```

取 `c=0`、`N=8`：

| d | slot | rounds | 被访问的 tick | 真正到期 tick |
|---|---|---|---|---|
| 1 | 1 | 0 | 1 | 1 |
| 8 | 0 | 0 | 8 | 8 |
| 9 | 1 | 1 | 1、9 | 9 |
| 16 | 0 | 1 | 8、16 | 16 |
| 17 | 1 | 2 | 1、9、17 | 17 |

如果写成 `rounds=(d-c)/N`，`d=8` 会得到 1：tick 8 只做减圈，直到 tick 16 才执行。这不是精度误差，而是算法错误。

一个简短证明是：令 `delta=d-c>0`，总能唯一写成 `delta=p+r*N`，其中 `1<=p<=N`。该槽第一次在 `c+p` 被访问，之后每 N 个 tick 再访问一次；需要跳过 r 次，故 `r=floor((delta-1)/N)`，第 r+1 次访问恰好发生在 d。

不同实现可能采用“先扫描当前格再推进”、不同 tick 起点，甚至不同 deadline 分桶方式。**公式必须与游标定义一起使用。**Netty 4.1 在线源码中的 `remainingRounds` 公式属于它自己的 tick 约定，不能只复制一行过来。[1]

### 2.4 圈数没有消除长任务的重复访问

若一个未取消、未重置任务在 `c_ins` 插入，到期 tick 为 d，那么它在此模型中总共被访问：

```text
ceil((d - c_ins) / N) 次
```

其中最后一次才触发，其余访问只递减圈数。一个很远的 deadline 若一直存活，会在每一圈给扫描路径增加工作。

增大 N 可以减少每桶压力与重复访问，却会增加桶元数据和管理成本；减小 u 会提升分桶精度，却缩短单圈时间跨度 `N*u`。两者都不是免费优化。

## 三、层级时间轮：把反复减圈变成按窗口降层

### 3.1 高层桶的时间，是搬迁时间，不是执行时间

经典层级时间轮让每层有 N 个槽，粒度逐层放大：

```text
g_l = N^l 个基础 tick
第 l 层一圈的时间跨度 = N * g_l * u
```

本文取 `N=8`、`u=10ms`：

| 层 | 每槽粒度 | 一圈跨度 |
|---|---|---|
| L0 | 1 tick＝10ms | 80ms |
| L1 | 8 tick＝80ms | 640ms |
| L2 | 64 tick＝640ms | 5120ms |

采用一种容易证明的分档：L0 接收 `1<=delta<N`；高层 l 接收 `g_l<=delta<N*g_l`，其中 `delta=d-c`。从低到高选择第一个容纳它的层。固定三层时，本文这套分档对 `delta>=512` 必须扩层、拒绝或交给溢出结构。

注意，单层模型允许 `delta=N` 留在本层并设 `rounds=0`；这里的层级模型把它送到上一层。这是两种明确的边界约定，不是必须混用的同一公式。

选定层后计算：

```text
q = floor(d / g_l)
slot = q % N
bucket_boundary = q * g_l
```

`bucket_boundary` 是高层桶应该被取出并降层的时间。原始 d 不变。

以 `c=0,d=73` 为例：

![层级时间轮：第 73 个 tick 到期的任务在 tick 64 和 72 降层，在 tick 73 进入就绪路径](/images/timing-wheel-hierarchy.svg)

- 初始剩余 73 tick，放 L2，桶边界是 `floor(73/64)*64=64`。
- tick 64 时仍剩 9 tick，不能执行，重定位到 L1，其桶边界为 72。
- tick 72 时剩 1 tick，重定位到 L0。
- tick 73 才真正满足目标到期条件。

**上层桶到期，不等于桶内每个任务到期。**如果直接执行上层整桶，例子中的任务会在 tick 64 提前执行。[2]

### 3.2 正确放桶，要保证目标绝对轮次尚未过去

环形索引只有余数，因此还要保证桶对应的是正确的绝对轮次。对于不带 rounds 的层，一个充分条件是：

```text
1 <= floor(d/g_l) - floor(c/g_l) <= N
```

它说明：目标桶起点在当前已处理时间之后，而且就是该槽未来第一次被访问的起点。

上面的完整分档能推出这个条件：`delta>=g_l` 保证不放到过去的高层桶；`delta<N*g_l` 保证不越过该槽下一轮。

反过来，只检查“delta 小于某层跨度”并不充分。例如 `c=10,d=15`，虽然 delta 只有 5、远小于 L1 的跨度 64，但放进 L1 槽 1 对应的桶起点是 8，已经过去；该槽下次到 72 才被访问。正确做法是放 L0。

这也是为什么跨整点、非零起始游标和整层边界，往往比“从零开始的示意图”更有测试价值。

### 3.3 级联必须保留 d，并处理同 tick 的到期

处理 tick k 时，应先处理该时刻需要级联的高层桶，按高层到低层的顺序下移，再处理 L0 当前桶。

内部下移有两个特殊规则：

1. 以当前处理时刻 k 为重定位基准，**保留原目标 d，不重新调用带 `max(c+1,D)` 的外部注册归一化逻辑**。
2. 若 `d<=k`，直接进入本 tick 的就绪路径；不能再人为加一个 tick。

边界例子 `d=64` 比 `d=73` 更能暴露问题：tick 64 既是高层桶边界，也是任务到期时间。如果下移时把它挪到 65，就平白增加一格；如果放进已扫描的 L0 槽 0，就可能晚一圈。

### 3.4 层级轮也不能笼统写成“全部 O(1)”

对固定 deadline、每次搬迁严格降低层级的经典模型：

- 逐层查找放置位置：一次 O(L)。
- 节点在层之间搬迁的次数：至多 O(L)。
- 若每次搬迁都重新从最低层逐层查找，整个生命周期的定位工作，保守上界可为 O(L²)。
- 若用固定宽度整数的位运算直接定位，或采用更直接的下降路径，可以减少定位成本；层数有固定小上限时，工程上常按常数讨论。

但这些都不意味着某一次 tick 是常数成本。一个高层桶有 m 个节点，搬迁它至少需要 O(m) 次节点处理；若每个节点还要 O(L) 重定位，这一桶可花 O(mL)。多层边界重合时，一次推进还可能处理多个桶。

**摊还成本用于估算长期总工作量，不能替代单次推进的尾延迟上界。**

### 3.5 少唤醒一次，有时比少做一次取模更有价值

朴素轮每个 tick 唤醒一次，任务稀疏时会空扫。另一种方式是维护“下一个需要处理的桶”，只在桶边界唤醒。

Confluent 2015 年对 Kafka request purgatory 的设计说明，给出了一种组合：层级时间轮维护任务，`DelayQueue` 维护桶，而不是每个任务。[2]

这个组合没有消灭优先队列，只是把它的规模从任务数 n，缩小到桶项数 B。桶级入队、弹出仍有 O(log B) 成本；取消任务后，空桶也可能继续留在延迟队列中，之后产生一次空唤醒。维护好每个桶的入队状态，才能避免重复桶项无限积累。

轮自身的空间是 O(n+N*L)，不是“只要固定 N*L，与任务数无关”。其中 n 应包含仍被引用、尚未回收的节点；命令队列、就绪队列、旧 generation 和唤醒索引还要另算。

## 四、取消语义与生命周期，比链表操作更容易出错

### 4.1 先让一个 owner 独占轮结构

一个容易推理的设计是：

```text
业务线程 / goroutine
        │ 注册、重置、清理通知
        ▼
有界命令队列 → 单 owner：挂链、摘链、级联、推进
                                  │ 到期且成功获得就绪名额
                                  ▼
                           有界执行队列 → worker
```

链表指针、桶归属、轮游标只由 owner 修改。生产者在调用时生成 absolute deadline；owner 收到命令后重新读 now，决定立即就绪还是入轮。不能到出队时才做 `now+delay`，否则会把命令排队时间偷偷加进超时期限。

Go 中，通过 channel 发送已初始化对象，发送与对应接收之间建立同步关系；这不等于发送者之后可以继续无同步修改同一对象。不可变配置、原子状态和 owner 私有字段必须分开。[3]

### 4.2 一个可说明白的取消契约

下面是本文建议的**自定义 API 语义**，不是 Go `Timer.Stop` 或 Netty `cancel` 的统一保证：

![定时器状态机：PENDING、READY 可取消；worker 赢得 READY 到 RUNNING 的原子转换后获得唯一执行权，运行结束进入 DONE](/images/timing-wheel-cancellation.svg)

- `PENDING`：已接受，尚未提交执行，可能在注册队列、轮或 owner 的过期积压中。
- `READY`：已取得就绪资格，正在发布到就绪队列或等待 worker，但尚未获得执行权。
- `RUNNING`：worker 已经获得执行权；不一定已经进入用户函数体。
- `DONE`：执行路径已结束。
- `CANCELLED`：该次注册不会再获得执行权。

关键原子竞争如下：

| 操作 | 尝试状态变化 | 成功的含义 |
|---|---|---|
| owner 标记就绪 | CAS：PENDING → READY | 没有被并发取消，允许交给执行路径 |
| worker 提交执行 | CAS：READY → RUNNING | 获得该次注册唯一的执行权 |
| Cancel | CAS：PENDING 或 READY → CANCELLED | 此后该次回调不会开始 |

owner 应先取得就绪队列名额，再 CAS 标记 READY，最后发布队列项；CAS 失败则归还名额。这样不会先承诺就绪、再因队列满而丢掉任务。发布期间被取消的队列项，由 worker 检查状态并清理。

worker 的成功 CAS 是执行权的提交点。若它先成功，Cancel 可以返回 false，哪怕线程随后被抢占、用户函数一行还没执行。

所以本文的契约是：

> Cancel 返回 true，保证该次注册不会启动；返回 false，不能推断回调已经结束，甚至不能推断它已经进入函数体。重复取消也可能返回 false。

Cancel 若在 PENDING 上 CAS 失败，可能只是 owner 已将它变为 READY，不能直接认定“已经执行”；需要重读状态，决定是否继续尝试。owner 也必须用条件迁移，不能读到 PENDING 后无条件写 READY，否则可能覆盖 CANCELLED，让任务复活。

### 4.3 逻辑取消、物理摘链、对象回收是三件事

CAS 成功只能决定“这次回调不再启动”。它不会自动完成：

- 从桶链表中删除节点。
- 从就绪队列移除残留引用。
- 等待已经运行的回调结束。
- 释放闭包捕获的连接、缓冲区或请求对象。

清理通知可以让 owner 执行 O(1) 摘链，但排队和回收没有因此变成 O(1) 时间保证。通知队列满时，需要有明确的延后清理或可恢复扫描机制，不能遗失清理责任。

C++ 中，原子状态不保护已释放对象；handle、队列项和 worker 引用都必须遵守所有权协议。`shared_ptr` 可以延长对象生命周期，却不自动同步对象成员。Go 的 GC 避免不了被长寿命定时器闭包持续引用的内存，也不会替你停止业务 goroutine。

若需要“返回时回调已经完全停止”的 `CancelAndWait`，必须额外等待完成信号；还要禁止或特殊处理回调内部等待自身结束，否则可能死锁。

### 4.4 Reset 要隔离旧句柄，不要简单把状态改回 PENDING

推荐让每次注册拥有独立 generation：身份、deadline、回调配置不可变；执行状态原子单向变化；链表字段归 owner。旧 handle 和旧队列项都绑定旧 generation。

这样可以避免旧取消命令误伤新任务，也减少复用节点地址带来的 ABA 风险。但 **generation 只隔离身份，不会停止已运行的旧回调**。

如果把 Reset 定义为“取消旧注册，再创建新注册”，它不天然具备原子替换语义。旧任务若已经 RUNNING，仍可能和新任务重叠。需要“只允许最新一代产生业务效果”时，应在业务提交处使用一致的版本条件或状态机仲裁，不能只在回调开头检查一次 generation 就假定之后永远有效。

## 五、精度、过载与证据：别把数据结构胜利当成系统胜利

### 5.1 单调时钟与唤醒次数不是一回事

相对超时应使用同一单调时钟域。在 Go 中，可以保留 `time.Now()` 返回的 `Time`，用 `Add` 生成 deadline、用 `Sub` 或比较方法计算相对时间；当两端都保留单调读数时，这些操作使用单调时钟。转换成 `UnixNano()` 或序列化会丢失这种读数，不能把整数 Unix 时间戳当作单调时间。[4]

单调时钟是否计入系统休眠，与平台有关；“空闲超时”是否应跨系统睡眠继续计时，需要业务明确。日历调度和跨重启任务还需要墙钟、时区、持久化等额外设计，不能靠一个内存时间轮包办。

每次醒来，应重新计算：

```text
target = floor((monotonic_now - t0) / u)
逐个处理 c+1 ... target，处理完一个 tick 才提交 c
```

不能把“收到一次 tick 通知”等同于“只经过一个 tick”。Go 官方明确说明，Ticker 在接收慢时可能调整间隔或丢弃 tick。[4] 如果暂停后只做一次 `c++`，整个时间轮会持续落后。

也不能直接把 c 跳到 target 后只扫描 `target%N`：跨过的槽、圈数扣减和级联都会遗漏。允许分批追赶，但预算耗尽时 c 必须停在真正处理完成的位置；若要跳跃式推进，需要额外证明它与逐 tick 处理等价。

### 5.2 分桶误差、推进延迟、执行排队要分别测

对正常轮内路径，设 e 是原 deadline，q 是量化后的名义刻度，r 是实际进入 READY 的时刻，b 是回调开始时刻：

```text
b - e = (q - e) + (r - q) + (b - r)
         量化误差    推进/扫描延迟    执行排队/调度
```

`u=1ms` 只约束第一项。暂停、热点桶、级联、owner 被抢占会增加第二项；回调耗时和执行器积压会增加第三项。

如果到期任务的长期到达速率超过执行器服务能力，队列就会增长。换成时间轮可能让“更快发现任务”的阶段更快，但无法保证更快完成任务。

生产实现至少需要：

- 有界注册队列与明确的接受、拒绝、背压语义。
- 有界就绪队列；满载时保留可恢复的到期积压，不能静默丢任务。
- owner 的扫描、级联和命令处理预算，避免持续注册饿死推进，也避免大桶饿死取消处理。
- 回调与推进路径隔离，并正确处理回调异常、执行器拒绝和关闭流程。

若业务允许宽松窗口，可以分散批量注册的相位或增加受控的非负抖动；硬 deadline 不能为追求均匀分桶而任意提前。限额和抖动都会改变语义或延迟，必须纳入 SLA。

### 5.3 一个可运行、但刻意不伪装成生产代码的验证模型

以下程序只验证**单层轮的整圈边界、非零起点、补齐跨过的 tick，以及 deadline 量化反例**。它不实现并发、取消、层级轮、时钟唤醒和真实回调。slice 追加存在扩容，因此不能拿这份代码证明生产侵入式链表的最坏 O(1) 插入。

运行环境：`go1.27.0 windows/amd64`；仅使用标准库。保存为 `wheel_demo.go` 后运行 `go run wheel_demo.go`。

```go
package main

import "fmt"

const slots int64 = 8

type timer struct {
    id     int
    due    int64
    rounds int64
}

type wheel struct {
    current int64
    buckets [8][]timer
}

// 仅接受已经量化、严格位于未来的逻辑 tick。
func (w *wheel) add(id int, due int64) {
    if w.current < 0 || due <= w.current {
        panic("due must be strictly after a non-negative current tick")
    }
    t := timer{id: id, due: due, rounds: (due - w.current - 1) / slots}
    i := due % slots
    w.buckets[i] = append(w.buckets[i], t)
}

func (w *wheel) advance(now int64) []timer {
    if now < w.current {
        panic("time must not go backwards")
    }
    var ready []timer
    for w.current < now {
        k := w.current + 1
        i := k % slots
        bucket := w.buckets[i]
        w.buckets[i] = nil
        for _, t := range bucket {
            if t.rounds > 0 {
                t.rounds--
                w.buckets[i] = append(w.buckets[i], t)
                continue
            }
            if t.due != k {
                panic("wrong expiration tick")
            }
            ready = append(ready, t)
        }
        w.current = k
    }
    return ready
}

func ceilDiv(n, d int64) int64 {
    if n < 0 || d <= 0 {
        panic("invalid ceilDiv input")
    }
    q := n / d
    if n%d != 0 {
        q++
    }
    return q
}

func main() {
    var w wheel
    for id, due := range []int64{1, 8, 9, 16, 17} {
        w.add(id, due)
    }
    for tick := int64(1); tick <= 17; tick++ {
        for _, t := range w.advance(tick) {
            fmt.Printf("tick=%d id=%d due=%d\n", tick, t.id, t.due)
        }
    }

    cases := 0
    for start := int64(0); start < 16; start++ {
        for delay := int64(1); delay <= 64; delay++ {
            x := wheel{current: start}
            due := start + delay
            x.add(7, due)
            if got := x.advance(due - 1); len(got) != 0 {
                panic("early expiration")
            }
            got := x.advance(due)
            if len(got) != 1 || got[0].id != 7 || got[0].due != due {
                panic("missing or duplicate expiration")
            }
            if got := x.advance(due + 2*slots); len(got) != 0 {
                panic("repeated expiration")
            }
            cases++
        }
    }
    fmt.Printf("boundary cases passed: %d\n", cases)

    var x wheel
    for id, due := range []int64{1, 8, 9, 16, 17} {
        x.add(id, due)
    }
    got := x.advance(17)
    if len(got) != 5 {
        panic("catch-up missed a timer")
    }
    for i, due := range []int64{1, 8, 9, 16, 17} {
        if got[i].due != due || got[i].id != i {
            panic("wrong catch-up order")
        }
    }
    fmt.Println("catch-up cases passed: 1")

    // 同一单调起点后的毫秒数：now=105，delay=10，u=10。
    correct := ceilDiv(105+10, 10)
    wrong := int64(105/10) + ceilDiv(10, 10)
    if correct != 12 || wrong != 11 {
        panic("unexpected quantization result")
    }
    fmt.Printf("absolute deadline tick=%d; relative shortcut tick=%d\n", correct, wrong)
}
```

本次实际运行输出：

```text
tick=1 id=0 due=1
tick=8 id=1 due=8
tick=9 id=2 due=9
tick=16 id=3 due=16
tick=17 id=4 due=17
boundary cases passed: 1024
catch-up cases passed: 1
absolute deadline tick=12; relative shortcut tick=11
```

1024 组来自 16 个起始 tick × 64 种正延迟；每组检查不提前、按目标 tick 恰好返回一次、之后不重复。追赶用例一次推进到 17，检查跨过的五个任务都被返回。它们支持本文这个有限范围模型的边界实现正确，**不证明所有整数范围正确，也不验证真实时间精度、并发取消或层级级联**。

### 5.4 性能实验应该怎样做

**未实测，以下为性能验证方案，不是跑分结论。**

待验证假设：在精度语义相同、高取消率、大量活跃任务的负载中，时间轮能减少索引维护 CPU；在集中到期或长时间暂停后，桶扫描、级联和执行积压可能抵消收益。

| 控制维度 | 建议覆盖的实验负载 |
|---|---|
| 活跃任务数 | 固定多个量级，避免只比较刚启动的空结构 |
| deadline 分布 | 均匀分散、全部同槽、刚好整圈、长短混合、远期长尾 |
| churn | 不取消、频繁取消、同一业务对象频繁重置；比例作为实验变量 |
| 暂停与过载 | 人工延迟 owner、执行器限速、命令队列满、就绪队列满 |
| 基线一致性 | 同一时钟、相同“不提前”语义、相同执行器与回调负载、相同取消保证 |

优先测量：注册调用耗时与注册命令排队时间；逻辑取消耗时与物理清理滞后；每 tick 扫描节点数与级联节点数；`r-q` 和 `b-r` 的 P50/P99/P99.9；CPU、分配速率、存活内存、拒绝数和队列峰值。

使用固定到达速率的开环负载检查过载，避免测试线程随服务变慢一起降速，从而漏掉排队问题。记录 Go/编译器版本、CPU、系统、核数与配额、预热、重复次数和采样开销；不能只选一次最佳值。

判据不应只是“注册吞吐更高”，而应是：在目标 SLA 下，时间索引的 CPU 或内存成本下降，同时真实回调延迟、拒绝率和取消清理延迟没有越界。若热点来自 callback 而非 timer 管理，应先解决执行器与业务负载。

### 5.5 看生产实现时，先对齐它的目标

- **Netty 4.1 在线源码**：是单层 wheel＋`remainingRounds`，新任务和取消通过队列交给 worker；它明确面向近似 I/O timeout，并提醒不要每连接创建一个实例。默认即时执行器会让长回调拖住推进路径。本文引用的是滚动文档，不是固定 release tag。[1]
- **Kafka 的公开历史设计**：Confluent 2015 年文章强调双向链表实现可定位摘链、层级轮处理远期任务、延迟队列按桶驱动。可借鉴机制，但不能把文中的微基准当作今天自己的服务收益。[2]
- **Go 1.23.0 的固定源码**：`runtime/time.go` 明确是每个 P 管理 timer heap，`timerHeapN=4`；它不是时间轮。`Stop` 和 `Reset` 还含有延迟清理与懒更新路径，不能从“底层是堆”直接断言每一次 API 调用都立即做 O(log n) 调整。[5]

这三个例子说明：不要从数据结构名倒推系统优劣。批量 timeout、通用定时服务、调度器内部 timer，约束并不相同。

## 六、资深岗位面试：六个值得追问的问题

P0/P1/P2 表示本文的复习优先级，不是统计命中率、公司职级或真题频率。

### P0-1：时间轮为什么能 O(1)，又为什么一次 tick 会卡很久？

**考察能力：**拆分复杂度口径，而不是背诵结论。

**30—60 秒核心回答：**单层轮把目标 tick 直接映射到数组槽，已知节点时挂链、摘链可常数完成；但当前桶有 m 个节点就要处理 m 个节点，包含减圈而未到期的任务。层级轮还要计算放置层、搬迁桶；执行 k 个到期任务至少有与 k 成正比的工作。固定层数让某些管理成本可视为常数，不会消除热点桶。

**约 3 分钟展开：**定义 n/m/L → 给出单层生命周期访问次数 → 区分级联次数和重定位成本 → 用集中到期反例解释尾延迟 → 把唤醒堆与内存分配加回成本账。

**三层追问：**

1. 为什么 `d=8,N=8,c=0` 的 rounds 是 0？答：首次访问槽 0 已经是 tick 8，不需要跳过任何访问；公式是 `(d-c-1)/N`。
2. 一百万个任务同一刻到期，换成层级轮能解决吗？答：不能。层级轮减少远期反复访问，但仍需处理这一百万个任务，还可能先集中级联。
3. 如何选型与回退？答：用相同精度、取消和执行器语义比较堆与轮，观测索引 CPU、级联量和真实 P99；若收益仅在微基准出现，或尾延迟越界，应保留/回退简单基线。影子验证只比较“应到期集合”，不能重复执行真实回调。

**常见误答：**“槽位固定，所以无论任务多少，所有操作都 O(1)。”

**加分点：**主动说明空间包含 O(n) 节点、懒删除留存，以及常数成本不包含排队等待。回看第二、三、五节。

### P0-2：取消返回成功，能不能立刻释放对象？

**考察能力：**线性化点、所有权与业务语义。

**30—60 秒核心回答：**不能直接推断。本文的取消成功只表示 CAS 赢过执行权提交，保证该次回调不再启动；桶、队列、handle 仍可能引用对象。物理摘链和对象回收要单独完成。若回调已经获得执行权，取消可以失败，等待其完成需要另一套协议。

**约 3 分钟展开：**画 PENDING/READY/RUNNING 状态机 → 展示 Cancel 与 worker 的两种 CAS 顺序 → 解释 owner 不可覆盖 CANCELLED → 列出所有持有引用的位置 → 说明同步等待与自等待死锁。

**三层追问：**

1. worker CAS 成功却尚未进入函数体，Cancel 应返回什么？答：可以返回 false，因为执行权已提交；“函数体没开始”不等于“仍可撤回”。
2. Reset 后旧回调仍在执行怎么办？答：新 generation 防旧句柄误伤，但不杀死旧回调。若只允许新版本提交结果，必须在业务提交处做一致的版本或状态仲裁。
3. 怎样验证并选择更简单方案？答：用屏障控制“就绪前、就绪后、CAS 后、函数体内”的交错，检查执行次数与引用释放；竞态检测只作补充。若跨线程取消契约难维护，优先让业务完成与超时仲裁归同一 owner，必要时通过确认消息等待结果。

**常见误答：**“用了 atomic/shared_ptr/GC，所以线程安全且可以立即释放。”

**加分点：**区分逻辑取消、结构删除和等待完成；指出 false 还可能表示此前已取消。回看第四节。

### P0-3：如何保证不提前触发？

**考察能力：**时间离散化与相位边界推导。

**30—60 秒核心回答：**用同一单调时钟域的 absolute deadline 向上取整到目标 tick；推进不得超过当前时间对应的完整刻度。入轮前已过期任务进入就绪路径。层级轮的高层桶只负责提前搬迁，最终仍按原 deadline/目标 tick 到期。

**约 3 分钟展开：**定义 c 与 t0 → 推导 D 的 ceil → 复现 105ms＋10ms 反例 → 推导纯量化误差 → 解释内部级联不能再次加一。

**追问：**“tick=1ms，是否保证一毫秒内启动？”答：不保证；只有量化部分小于一个 tick，推进、暂停和执行器排队没有被这一参数约束。

**常见误答：**“delay 向上取整，再加当前槽号即可。”

**加分点：**补充溢出、系统休眠、序列化丢失单调读数的边界。回看第二、三、五节。

### P1-4：暂停 500ms，轮子应该转多少格？

**考察能力：**从唤醒事件恢复逻辑时间，以及过载处理。

**30—60 秒核心回答：**根据单调时钟重新算 target，从已处理的 c 追赶，而不是根据收到了几个通知决定。逐 tick 模型要补齐中间的桶扫描、rounds 扣减和层级级联；可以限制每批工作预算，但不能把未处理时间假装提交掉。

**约 3 分钟展开：**区分时钟与通知 → 构造跨过多个桶的例子 → 说明直接改游标会漏任务 → 分离追赶预算与执行预算 → 观测积压何时恢复。

**追问：**“暂停后周期任务漏了十次，补跑十次吗？”答：这是 API 语义，不是时间轮决定的。固定延迟、固定频率，以及漏跑后补齐/合并/跳过应明确选择；补跑策略还必须受预算限制，避免恢复时形成风暴。

**常见误答：**“Ticker 每收到一次就加一，不会漏。”

**加分点：**说明更聪明的跳跃式推进可以做，但必须重新证明轮次与级联等价。回看第五节。

### P1-5：注册吞吐提升了，为什么 P99 反而变差？

**考察能力：**证据分解与排除竞争假设。

**30—60 秒核心回答：**可能是索引更快、到期发现更集中，瓶颈转移到桶扫描、级联或执行器。先记录 deadline、量化 tick、READY 和回调开始时刻，分开看量化、推进和执行排队；再与每 tick 扫描量、队列长度、CPU/GC/调度证据对齐。

**约 3 分钟展开：**建立三段延迟模型 → 比较均匀与同槽负载 → 检查 owner 是否执行用户回调 → 检查开放负载下的积压 → 控制相同回调成本做基线实验。

**追问：**“增加 worker 一定有用吗？”答：只有执行器是瓶颈且业务可并行时才可能有效；若瓶颈在 owner 单线程级联，或回调争用同一锁，多 worker 可能没有改善甚至增加争用。

**常见误答：**“一定是 GC，先调 GC 参数。”

**加分点：**不仅报吞吐，也报告拒绝率、清理滞后和端到端尾延迟，允许证据否定时间轮方案。回看第五节。

### P2-6：既有少量精细 deadline，又有大量远期粗粒度任务，怎么设计？

**考察能力：**约束分层与有条件的工程决策。

**30—60 秒核心回答：**先明确精细任务是否真的要求硬实时、允许多大误差、远期任务是否需要跨重启。若两类语义确实不同，可用堆管理近期精细 deadline、时间轮管理粗粒度或远期任务；临近时迁移。但混合会新增迁移、取消、唤醒和统计口径，规模不足时一个堆更好。

**约 3 分钟展开：**列 SLA 与范围 → 比较单堆/单轮/混合 → 设计迁移期间的唯一执行权和 owner → 校验取消与溢出 → 定义影子对账、灰度和回退判据。

**追问：**“要求进程重启后任务不丢呢？”答：增加持久化任务记录、恢复扫描和幂等执行；内存轮只作时间索引或缓存。恢复期间如何处理已过期任务和重复副作用，要由业务协议保证，不能宣称时间轮本身可靠投递。

**常见误答：**“层数足够多就什么都能解决。”

**加分点：**主动给出不采用混合方案的条件：维护复杂度大于可测收益，或者任务语义本来没有分层必要。回看第一、三、四、五节。

## 七、60 秒复盘

1. **允许时间离散化、任务规模或取消 churn 足够高时，时间轮才可能值得采用。**先与带索引的堆做同语义比较。
2. **游标定义决定公式。**本文单层模型的 `rounds=(d-c-1)/N`，保护的是整圈边界；absolute deadline 的 ceil 保护“不提前”。
3. **高层桶只意味着进入更近的窗口。**保留原始 deadline，正确级联到低层，才不会提前执行或多等一圈。
4. **取消执行权、物理摘链、回收对象互不等价。**状态机、owner、generation 和生命周期必须一起设计。
5. **量化误差不是回调延迟上界。**把推进积压、级联和执行排队分别测量；当复杂方案不能改善目标 SLA 时，应选择更简单的实现。

决策主线：**超时契约 → 时间分桶 → 放桶/级联不变量 → 执行权与回收 → 同语义证据 → 采用或放弃。**

三个自测问题：`d` 刚好等于一整圈时会不会晚一圈？取消在 READY→RUNNING 两侧分别承诺什么？owner 暂停跨过多个桶后，会不会漏掉任何一个到期任务？
